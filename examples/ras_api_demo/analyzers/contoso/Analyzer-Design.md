# Contoso CPER Analyzer

## Objective

Provide example code for time-series CPER analyzers intended to work with the RAS API.  RAS API endpoints emit CPERs when they detect a hardware error.  The RAS API provides a universal framework for routing the CPERs to CPER Analyzers and CPADs from the CPER Analyzers back to endpoints to trigger RAS actions that mitigate the underlying fault that caused the error to be detected.


## RAS API Context

The example code integrates into the RAS API demo. It supports discovery by the Analysis Orchestrator.  It takes a list of CPERs as an input.  It starts by validating and analyzing the newest CPER in the list and optionally outputs the decoded CPER in JSON format.  The details of the decoding are described below.  If the analyzer is able to infer that there is a hardware fault that could be mitigated by a RAS action such as a DDR Post Package Repair or manual intervention (part replacement, etc.), it will emit a CPAD containing the details needed to drive the action.  This CPAD will be evaluated by the Server Fleet Operator Policy Engine.  If the policy engine allows the CPAD to proceed, it will either send the CPAD back to the endpoint to trigger a RAS action on the endpoint or forward the CPAD to data center automation to trigger a manual intervention such as a part replacement.

### CPER Input Requirements
- Contract: 
  - RAS API provides an abstraction layer that allows Server Fleet Operators to collect CPERs from hardware
     - even when the Server Fleet Operator does not know what the hardware is
     - for any hardware endpoint that supports RAS API
  - CPERs generated by RAS API endpoints can be interpreted by the CPER Analyzer intended for that endpoint
  - The CPER headers can be parsed by the error collection pipeline to route the CPERs to the correct analyzer
  - The CPER bodies may be opaque to the server fleet operator's pipeline/code
  - The CPER bodies are understood by a vendor's analyzer for the same vendor's RAS API endpoints
  - A CPER section indicates that some functional subcomponent of the silicon detected one or more errors
  - A CPER section may log one or more hardware errors
  - Multiple CPER sections might log the same error from different functional subcomponents viewpoints
  - The Analyzer must never count CPER sections to infer the number of errors

### JSON Decoding Requirements

The decoded JSON data consists of two parts:

1. A summary of the CPER
    - From the Header: PlatformID, PartitionID, Timestamp, RecordID, Header "Flags" field
    - If the CPER contains error information:
        - A summary of the errors logged in the CPER
            - Name of the error
            - CPER severity of the error
            - FRUID from section descriptor
            - FRU Text from section descriptor
            - This summary can be a cumulative summary of the CPER or a section by section summary of the errors in the CPER
        - A list of zero or more ActionIDs (numbers and string descriptions) from CPADs suggesting actions to mitigate the error(s)
        - a text message telling the user about the error
            - if the error does not represent a risk of crashing the machine or a risk of a performance problem, let the user know that no action is needed
            - if the error is a know issue with the chip, include a bug identifier for the issue that the customer can reference
    If the CPER contains a Platform Action Event:
        - the action ID and a descriptive string for that Action ID
        - the action status value and descriptive string for the value
        - the action status reason code and a descriptive string for the reason code
        - a text message for the user that tells them that the action was completed, the action failed and some other action needs to be taken

2. The fully decoded CPER
   - CPER Header
   - For Each CPER Section
    - The CPER Section Decriptor
    - The contents of the CPER section body
    - Including field-level parsing of all of the registers captured in the CPER
